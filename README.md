# Анализатор зависимостей NuGet — вариант 11

Практическая работа № 2 по дисциплине «Конфигурационное управление».
Kotlin/JVM, JDK 21, Gradle 8.13. Выполнены этапы 1–3: CLI, прямые зависимости NuGet и рекурсивный BFS.
Первая практическая работа сохранена в ветках `main`, `stage-4`, `stage-5`.

## Сборка и запуск

```sh
./scripts/gradle.sh clean test installDist
./run.sh --package Newtonsoft.Json
```

Нужен установленный Gradle 8.13 или его стандартный кеш. Можно указать
`GRADLE_BIN=/путь/к/gradle-8.13/bin/gradle`. При первой сборке нужен интернет
для Kotlin и JUnit. Бинарный Gradle Wrapper не включён по правилам задания.
Скрипт запуска можно вызывать из любого каталога; локальные пути аргументов
интерпретируются относительно текущего каталога вызывающей оболочки.

## Настройки

Все параметры задаются парами `--опция значение`, в любом порядке, без повторов.

| Опция | Значение и проверка |
| --- | --- |
| `--package` | Обязательное имя NuGet, до 128 символов: буквы, цифры, `_`, `.`, `-`. |
| `--repository` | HTTP(S) URL, по умолчанию `https://api.nuget.org/v3/index.json`. |
| `--test-mode` | `true` или `false` (по умолчанию); в режиме `true` источник — файл. |
| `--ascii` | `true` — ASCII-дерево; `false` (по умолчанию) — список смежности. |
| `--max-depth` | Целое число от 0 до 2147483647, по умолчанию 3; глубина корня — 0. |

В тестовом режиме имя состоит только из больших латинских букв `[A-Z]+`,
а `--repository` указывает существующий читаемый файл. Пустые значения,
неизвестные и повторные опции, некорректный URL, имя, глубина и логические
значения завершают приложение с кодом 2 и сообщением в stderr.
В ветке `practice2-stage-1` программа выводит все пять настроек
в формате `ключ=значение`. Ветка `practice2-stage-2` вместо диагностики выводит прямые зависимости.
Текущая ветка `practice2-stage-3` строит транзитивный граф.

## Проверка ошибок

```sh
./scripts/demo-config-errors.sh
```

Скрипт проверяет ошибки всех пяти параметров, неизвестные и повторные опции,
а также отсутствие значения. Успешная обработка каждого случая даёт код 2.

## Структура и функции

`src/main/kotlin/nuget/Config.kt`: `parse` проверяет опции, `describe` формирует
вывод настроек; приватные функции проверяют пары, булевы значения, глубину,
имя и источник. `Main.kt`: `main` запускает CLI и сообщает об ошибках.
Назначение каждой функции описано в KDoc. `tests/CliConfigTest.kt` проверяет
корректный ввод, значения по умолчанию и ошибки. Отчёт JUnit находится
в `build/reports/tests/test/index.html`.

## Получение зависимостей — этап 2

```sh
./run.sh --package Microsoft.Extensions.Logging
./run.sh --package Newtonsoft.Json --repository https://api.nuget.org/v3/index.json
./run.sh --package Newtonsoft.Json --repository https://api.nuget.org/v3-flatcontainer/
```

Поддерживается service index V3 либо URL каталога PackageBaseAddress с завершающим `/`.
Из service index читается ресурс `PackageBaseAddress/3.0.0`; из списка версий
выбирается последняя стабильная версия числовым сравнением. Если стабильных
версий нет, программа сообщает об ошибке. Информация берётся из `.nuspec`.
В выводе этапа 2 сохраняются имя, объявленный диапазон и framework зависимости.
На этапе 3 выводятся имена узлов и рёбра графа.
Пакет без зависимостей выводит `(нет)`. HTTP-ошибки, ошибки сети и повреждённые
документы завершают работу с кодом 1. Таймаут подключения и запроса — 30 секунд.

Версия и целевая платформа не задаются в варианте 11. Поэтому анализируется
объединение всех framework-групп последней стабильной версии каждого пакета.
Это граф отношений между именами пакетов: диапазоны версий на этапе 2 показываются
как метаданные, разрешение конфликтов версий и выбор совместимого framework
как при `dotnet restore` не выполняются. Никакие пакеты не устанавливаются.

`Repository.dependencies` задаёт контракт источника; `Dependency` хранит ребро.
`NugetRepository.dependencies` получает и кеширует зависимости, `discover`
находит API, `load` читает версии и XML, `compareVersions` сравнивает версии,
`directory` нормализует URL. `HttpTransport.get` выполняет HTTP-запрос.
`Nuspec.dependencies` использует защищённый XML-парсер JDK; DTD и внешние
сущности запрещены. Приватные функции разбирают дочерние элементы и группы.
`Json.parse` и `JsonReader` реализуют разбор JSON рекурсивным спуском;
`jsonObject`, `jsonArray`, `string` проверяют ожидаемые типы полей.
`NugetRepositoryTest` проверяет настоящий локальный HTTP-сервер, выбор версии,
framework-группы, кеш, HTTP-ошибки, повреждённый XML и запрет XXE.
`JsonTest` проверяет JSON и ошибки его синтаксиса.

Описание протокола: [Package content API](https://learn.microsoft.com/en-us/nuget/api/package-base-address-resource)
и [nuspec](https://learn.microsoft.com/en-us/nuget/reference/nuspec).

## Тестовый репозиторий и BFS — этап 3

```sh
./run.sh --package A --test-mode true --repository examples/diamond.txt --ascii true
./run.sh --package A --test-mode true --repository examples/cycle.txt --max-depth 5
./run.sh --package A --test-mode true --repository examples/chain.txt --max-depth 2
./scripts/demo-stage3.sh
```

UTF-8 файл содержит по одному объявлению на строку. Имена — `[A-Z]+`,
пустые строки и строки, начинающиеся с `#`, пропускаются. Каждый упомянутый
пакет нужно объявить; повтор объявления и неверное имя являются ошибкой.
Порядок объявлений не важен; повтор одного ребра удаляется.

```text
A: B C
B: D
C: D
D:
```

При `--ascii true` результат для этого файла:

```text
A
|-- B
|   `-- D
`-- C
    `-- D [seen]
```

Без ASCII-флага выводится `A -> B, C`, затем остальные узлы в порядке BFS.
Лист обозначается `(нет)`, непроверенная граница — `? [depth-limit]`.
`[seen]` означает уже выведенный узел: общий потомок или цикл; ребро сохраняется.

`GraphBuilder.breadthFirst` — рекурсивный BFS по фронтам: весь текущий уровень
обрабатывается до следующего. `tailrec` преобразуется Kotlin-компилятором
в цикл и не расходует стек на глубоких графах. Посещённые пакеты учитываются
без регистра, согласно правилам имён NuGet. Каждый пакет читается один раз.
Кратчайшие расстояния от корня находятся в `DependencyGraph.depths`.

Глубина корня — 0. При `--max-depth 0` показывается только корень, без запросов
к NuGet. При 1 читаются только зависимости корня; при 2 — ещё зависимости его
прямых потомков. Вершины границы показываются, но их зависимости не запрашиваются:
они могут быть листьями или иметь ещё зависимости. Поэтому пометка границы
не утверждает наличие потомков. Локальный файл полностью проверяется до обхода,
включая наличие корня и корректность недостижимой части графа.

`examples` содержит лист, цепочку, ромб, цикл, петлю и несвязный граф.
`demo-stage3.sh` показывает каждый случай и глубины 0, 1, 2.
Повреждённый граф, отсутствующий пакет и ошибки чтения дают код 1;
отсутствующий или нечитаемый файл в параметрах — код 2. Успешный запуск — код 0.

`FileRepository.read/fromText` читают и проверяют тестовый граф, `dependencies`
возвращает рёбра, `contains` проверяет корень. `GraphBuilder.build` создаёт
отдельное состояние обхода, `breadthFirst` раскрывает фронты, `canonical`
объединяет варианты регистра. `GraphOutput.lines` выводит список смежности.
`AsciiTree.render` строит дерево явным стеком, `suffix` помечает повтор и границу,
`appendChildren` сохраняет порядок ветвей. `Main.repository` выбирает источник.
`GraphTest` проверяет BFS, цикл, ромб, регистр, границу и цепочку глубиной 3000;
`FileRepositoryTest` проверяет файлы, листья и неверные объявления.

## История этапов и оформление

Каждый этап сохранён отдельным Conventional/Scoped Commit и отдельной веткой:
`practice2-stage-1`, `practice2-stage-2`, `practice2-stage-3`.
Для демонстрации исторического вывода этапа 1 или 2 переключитесь на его ветку,
выполните `./scripts/gradle.sh clean test installDist` и запустите пример выше.
На этапе 3 вывод настроек и временный вывод только прямых зависимостей заменены
выводом всего графа, как предусматривает условие «только для этого этапа».
Этапы 4–5 (обратные зависимости, Mermaid и изображение) не входят в эту сдачу.

В Git не включаются PDF задания, бинарные файлы, архивы, результаты сборки,
кеши, настройки IDE и локальная документация. Исходники и тесты используют KDoc.
Файлы ограничены 1000 строками, строки Kotlin — 100 символами, функции — 40 строками,
аргументы функций — семью, цикломатическая сложность — десятью.
